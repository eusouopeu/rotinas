# AGENTS.md

Guia de contexto do projeto **Brita** para o Codex. Objetivo: evitar que cada sessão precise re-explorar o repositório do zero — leia este arquivo primeiro, e use grep/busca direcionada no `index.html` (~9300 linhas) em vez de carregá-lo inteiro sempre que possível.

## Localização

`/Users/pedro/Codigos/Apps/Brita`

## O que é

PWA (Progressive Web App) chamado "Rotinas" (nome interno do projeto: Brita): rotinas cronometradas, notas rápidas em markdown, modelos de lista/matriz, e gerenciador de tarefas de estudo — tudo local-first, sem backend.

## Stack e ambiente

- **Sem framework, sem bundler.** HTML + CSS + JavaScript vanilla, tudo em um único arquivo `index.html` (CSS em `<style>`, JS em um IIFE **async** no fim do body). Não introduzir React/Vue/bundlers a menos que explicitamente solicitado.
- **Persistência**: helpers síncronos `load(key, fallback)` / `save(key, val)` / `removeKey(key)` sobre um **espelho em memória** (`mem` Map), com gravação assíncrona enfileirada num backend: **IndexedDB** no navegador, **Capacitor Filesystem** (um JSON por chave em `Directory.Data/brita/`) no APK. Migração automática do localStorage legado na primeira execução. Nunca usar `localStorage` diretamente.
- **APK Android via Capacitor 8** (plugins: filesystem, local-notifications, share). `isNative` distingue os ambientes; código nativo fica em ramos `if(isNative)`. Compilar: `npm run apk` → `android/app/build/outputs/apk/debug/app-debug.apk`. Exige JDK 21 (baixado pelo Gradle via foojay; caminho fixado em `android/gradle.properties`) e SDK em `~/Library/Android/sdk` (`android/local.properties`). Assinatura: `android/brita.keystore` (gitignorado — repo público; senha `brita-rotinas`; **manter cópia fora do repo**, sem ele a assinatura muda e o Android exige reinstalar).
  - **Sempre bumpar `versionCode`/`versionName` em `android/app/build.gradle` antes de gerar um APK que vai para o celular do Pedro.** Com `applicationId` e assinatura estáveis, o instalador do Android trata um `versionCode` igual ao já instalado como "nada para atualizar" e em vários aparelhos só oferece "Abrir" em vez de reinstalar de fato — sintoma: Pedro reinstala e as mudanças não aparecem, mesmo desinstalando antes. Aconteceu de verdade em 2026-07-28. `aapt dump badging <apk> | grep package:` confirma o que ficou empacotado antes de mandar. Há também um selo de build em Configurações → Dados (`BUILD_STAMP`, perto do topo do IIFE) — atualizar a cada build para o Pedro conseguir confirmar visualmente qual versão está rodando.
- **PWA**: `manifest.json` + `sw.js` (stale-while-revalidate; `CACHE_NAME` agora só limpa caches antigos, deploys chegam no reload seguinte sem bump manual).
- **Fontes locais** em `fonts/` (Fraunces títulos, Inter corpo, IBM Plex Mono dados — woff2 subset latin, sem rede).
- **Rodar localmente**: servir os arquivos estáticos (ex. `python3 -m http.server`). **Testar**: `npm test` (smoke test jsdom + fake-indexeddb: boot, migração, persistência — rodar após qualquer mudança no index.html).
- No APK, exports usam `nativeWriteExport()` → `Documentos/<pasta>/` (+ share sheet); blob/`<a download>`/`window.print()` não funcionam no WebView. Auto-backup nativo a cada 3 dias no mesmo lugar. Notificações de rotina são pré-agendadas como recorrentes do Android (`syncNativeSchedules`). **O nome da pasta é configurável** (`K_DATAFOLDER`, padrão `"Rotinas"`, `dataFolderName()`/`sanitizeFolderName()`) em Configurações → Backup — vale para exports, auto-backup e o espelho markdown (`Documentos/<pasta>/Notas/`). Trocar dispara `migrarPastaDados(antigo, novo)`, que move os arquivos já existentes (raiz + `Notas/`) via `readFile`/`writeFile`/`deleteFile`, best-effort; `obj._mdPath` de notas/modelos não é reescrito na migração — se autocorrige sozinho no próximo `syncMdFile` (a tentativa de apagar o caminho antigo só falha silenciosamente porque o arquivo já foi movido). Só afeta o app nativo — a store de dados viva (`Directory.Data`, que o widget lê direto via `RoutineStore.java`) continua fixa de propósito, mexer nela quebraria o widget.

Cuidado com TDZ: o auto-backup nativo chama `backupData()` no boot, então tudo que ela referencia tem de estar declarado no topo do IIFE, junto dos outros `load()`.

## Padrão de arquitetura (importante — ler antes de editar)

- **Estado de navegação**: uma variável global `view = { tab, screen, id? }`. Trocar de tela = reatribuir `view` e chamar `render()`.
- **Dispatcher central**: a função `render()` (linha ~1021) lê `view.screen` e chama a função `renderX()` correspondente (`renderHome`, `renderTemplates`, `renderTarefas`, `renderRoutineDetail`, etc.). Para adicionar uma tela nova: criar `renderNovaTela()` e adicionar um `else if` no dispatcher.
- **Renderização**: cada `renderX()` monta um elemento via template string (`el.innerHTML = ...`) e registra os handlers (`.onclick`, `.oninput`) depois de inserir no DOM. Não há virtual DOM — é *replace* do conteúdo da tela a cada render.
- **Dados**: arrays globais carregados via `load()` no boot (`routines`, `notes`, `templates`, `tarefas`, `history`, etc.), com uma constante `K_*` por chave (`K_ROUTINES`, `K_TEMPLATES`, `K_TAREFAS`...). Qualquer alteração de dado é seguida de `save(K_X, x)` (ou o helper específico, ex. `saveTemplates(doc)`). O boot aguarda `storageBackend.getAll()` no topo do IIFE async antes de qualquer render.
- **IDs**: gerados com `uid()` (string aleatória base36), nunca incrementais.
- **Gamificação (boletim)**: `K_GAMIFICACAO` guarda `config` (multiplicadores editáveis em Configurações), `semanaAtual` (fator de normalização **congelado** no domingo — não recalcular durante a semana), `historico` e `badges`. O fator vem de `fatorNormalizacaoPara(totalBruto)`: sem nenhuma etapa agendada ele **não pode ser 0** (zerava toda a pontuação da semana, inclusive tarefas de estudo) e cai numa escala padrão de 20 blocos médios de 30 min = 100. Cada conclusão guarda o peso bruto em `pb`, o que permite `repararFatorSemanaAtual()` reescalar semanas antigas salvas com fator 0. Pontos são creditados **etapa a etapa** em `pontuarEtapaConcluida()`, nunca em lote no fim — é o que faz conclusão parcial valer. Viradas de semana/mês/ano são resolvidas no boot por `avancarGamificacaoAteAgora()`, porque o app pode ficar dias fechado.
- **O dia de início da semana é configurável** (`K_WEEKSTART`, `weekStartDow()`, padrão domingo=0). `inicioSemanaISO(date)` devolve o dia configurado que abre a semana da data dada — **nunca** recalcular "início da semana" com `d.getDate()-d.getDay()` solto em outro lugar, sempre passar por `inicioSemanaISO`/`isoToDate(inicioSemanaISO(...))`, senão essa parte da tela ignora a configuração. Existem **duas convenções de "dia" diferentes** e é fácil confundir: `diaSemanaHoje()`/`Date.getDay()` são **literais** (0=domingo..6=sábado, para casar com `schedule.days` da rotina, que é sempre literal); `agendaCongelada[].dia`, `esperadoAte`, `construirAgendaSemana` e as chaves `"kanban:..."` usam **offset dentro da semana configurada** (0=primeiro dia configurado..6=último) — a conversão entre as duas é sempre `offsetSemana(diaLiteral)`. `ordemDiasSemana()` devolve os 7 dias literais na ordem de exibição (gráficos, calendário mensal, agenda semanal do Diário) — usar para reordenar colunas em vez de assumir domingo primeiro. A semana conta para o mês em que **termina** (`anoMesDoFimDaSemana`). Trocar o dia em Configurações reancora a semana em curso na hora via `reancorarSemanaAtual` (preserva o que já foi concluído dentro da nova janela, descarta o resto, reescala pelo novo fator — mesmo formato de `congelarSemana`/`repararFatorSemanaAtual`, todos passando pelo helper `fatorParaArea`). Havia uma base segunda-feira fixa antes: duas migrações de boot cuidam do legado — `migrarSemanaParaDomingo` (reancora `semanaAtual` uma única vez, com o flag `gam.semanaMigradaDomingo` — **sem esse flag**, configurar um início diferente de domingo faria essa migração achar de novo que `inicioISO` está "errado" e desfazer a preferência do Pedro a cada boot) e `migrarSemanasDoDiario` (chaves `semana:<segunda>` viram `semana:<domingo anterior>`).
- **Peso "nenhum"**: quarta opção de `tagValor` (além de baixo/médio/alto) com multiplicador fixo 0 — `gam.config.multiplicadores.nenhum` é reescrito para 0 no boot e não aparece em Configurações. `pesoBruto` devolve 0, então a etapa some da agenda congelada e `registrarConclusao` devolve `null`: a rotina roda normalmente e não pontua. `distribuicaoTags()` deixa essas etapas fora do `total`.
- **Roda da vida** (`gam.config.roda = {ativa, areas:[{id,label,color,peso}], pesoSemArea}`): com ela **ativa**, os 100 pontos da semana são repartidos primeiro ENTRE as áreas (proporcional ao `peso` de cada uma) e só depois entre as rotinas de cada área — é o que tira rotinas de áreas diferentes da mesma disputa. `fatoresPorArea()` devolve um fator por área; área **sem nada agendado não reserva fatia**, senão a semana não fecharia 100. A rotina aponta a área em `r.eixo`, e as áreas são **semeadas dos `EIXOS`** com os mesmos ids — assim a tarefa de estudo (que já tem `m.eixo`) cai na mesma área sem migração. Cada entrada de `concluidos` guarda `area`, o que alimenta `pontosPorAreaSemana()` (seção do boletim) e o reescalonamento de `repararFatorSemanaAtual`. Desligada, `fatoresPorArea` devolve `{}` e tudo volta ao fator único.
- **Hábito consolidado** (`gam.config.habito = {ativo, streakMin, fator}`): rotina com streak ≥ `streakMin` passa a valer `fator` (padrão 0,6) do peso, abrindo espaço para o que ainda não pegou. O estado é decidido **uma vez, no congelamento de domingo**, e guardado em `semanaAtual.habitos` — se dependesse do streak vivo, o peso das etapas mudaria no meio da semana e a agenda congelada deixaria de bater. `construirAgendaSemana(mapaHab)` recebe o mapa por parâmetro justamente por isso (congelar passa um novo, reparar passa o congelado). Opt-out por rotina em `r.semHabito`.
- **Vagas excludentes de peso** (`gam.config.vagas = {alto, medio, baixo}`, 0 = sem limite): quantas rotinas podem ocupar cada nível — **dentro da área** quando a roda está ativa, global quando não. O limite é cobrado **no salvar** (`validarVagaPeso`), não no clique da pílula: rebaixar outra rotina por causa de uma edição que ainda pode ser cancelada deixaria o dado dela errado sem nada ter sido salvo. No editor, `vagaHintHtml()` só informa quem ocupa. Toda essa lógica (roda, hábito, vagas) é coberta por `test/gamificacao.cjs`.
- **Markdown**: `renderMdBlock(texto, chave, msgVazio)` é o renderizador de leitura (negrito, listas, checklist clicável, toggle), usado no overlay de nota e no journaling. Não criar outro parser.
- **Editor contínuo (live preview)**: `renderLiveEditor()` é a superfície de escrita das notas — um único `contenteditable` (`#liveEditor`) em que toda linha aparece formatada, menos a do cursor, que mostra o markdown cru. Modelo do Obsidian. Regras: o texto é a fonte da verdade; **digitação comum é nativa** na linha crua (não interceptar — quebraria o IME/autocorreção do Android) e o `input` só relê essa linha; **edições estruturais são interceptadas** no `keydown` (Enter, Backspace no col 0, Delete no fim, seleção multi-linha) e no `beforeinput` (rede para teclados que só emitem `inputType`), sempre via `liveAplicar(a, b, texto)`. Redesenhar o `innerHTML` destrói o nó focado, então `liveColocarCursor()` **precisa** devolver o foco no mesmo ciclo. A fonte do texto é plugável por `liveCtx` (`noteLiveCtx()` para Notas simples, `diarioLiveCtx()` para o Diário) — só existe uma instância por vez. As anotações de journaling ainda usam o lápis + textarea porque exigiriam várias instâncias simultâneas. Lógica coberta por `test/editor.cjs`.
  - **Barra de atalhos markdown** (`.md-toolbar`, `MD_TOOLBAR_BOTOES`, `ensureMdToolbar`): B/I/título/lista/lista numerada/checklist/recuo±, fixa acima do teclado virtual (posição por `visualViewport`), visível só com `liveFocado`. **A ação roda no `pointerdown`, nunca no `click`** — o `preventDefault` necessário para não tirar o foco do editor cancela os eventos de compatibilidade que o navegador sintetiza no toque, inclusive o `click`; por isso os botões funcionavam no desktop (onde o `mousedown` não cancela o click) e **não funcionavam no celular**. Escondida no desktop, onde existe teclado físico.
  - **Indentação**: `INDENT_PASSO` (2 espaços) + `nivelIndent()`/`partesIndent()`, junto das constantes de parsing (não lá embaixo na barra — `renderMdBlock` e `renderLiveEditor` usam `nivelIndent` e ficariam em TDZ). O recuo vira `margin-left` **na linha crua também, com o mesmo valor**: recuar só a formatada faria o texto pular de lado quando o cursor entrasse na linha. Os botões de lista/título preservam o recuo via `partesIndent` — um `.trim()` solto devolveria a linha para a margem.
  - **A linha do cursor não pode virar uma caixa.** Ela já teve fundo próprio, barra lateral de acento e padding extra, e o título caía de 24px para 15px ao entrar em edição: o texto pulava e o editor "parecia" trabalhar linha a linha em vez de ser um texto corrido — foi reclamação explícita do Pedro. Hoje `.live-raw` é transparente e `classeCruaDaLinha()` devolve à linha crua a tipografia do bloco (`.live-raw-h1/h2/h3`, `.live-raw-li`), então nada muda de tamanho nem de posição quando o cursor entra e sai. Não reintroduzir realce de caixa.
  - A linha crua **precisa continuar sendo um único nó de texto** (`div.textContent = raw`): `liveColocarCursor()` posiciona o cursor em `div.firstChild`. Por isso o destaque da sintaxe é feito por CSS na div, e não embrulhando pedaços em `<span>`.
- **Metas** (aba própria, antes "Contagens regressivas" em Modelos): os dados continuam num doc `type:"countdown"` para não exigir migração — só a apresentação mudou. O escopo vem do prazo (`metaEscopo`: <30 dias mensal, 30–90 trimestral, >90 anual) e o bônus vai para `gam.metasPontos[periodo]`, somado à nota do período no fechamento. A aba **Tarefas** saiu da tabbar para dar lugar a Metas e agora é acessada pelo ícone ☰ no header da home.
  - **Prazos vs. Recorrentes**: toggle multiselect (`metasSubviewSel`, `K_METASSUBVIEWSEL`) — os dois podem ficar visíveis juntos (`ambos`), nunca os dois desmarcados. **Recorrentes é a primeira opção e o padrão** para quem nunca tocou o toggle (fallback em `metasSubviewSel`); Prazos vem depois.
  - **Metas recorrentes** (`doc.recorrentes`, hábitos que repetem N vezes ao dia/semana — ver `metaRecPeriodoAtual`/`metaRecProgresso`) podem ser **negativas** (`rec.negativa`, ex.: "delivery no máx. 2x/semana"): `rec.vezes` vira o LIMITE em vez do alvo, e cada marcação além do limite (`metaRecExcesso`) credita uma penalidade **negativa** na semana corrente (`sincronizarPenalidadeMetaRec` empurra/remove entradas em `gam.semanaAtual.concluidos` com `tipo:"metaRecNeg"`, itemId estável `metarecneg:<recId>:<periodo>:<n>` para poder estornar ao desmarcar). O peso da penalidade é `rec.tagValor` (nenhum/baixo/médio/alto, padrão médio) via `pesoBruto` — mesma "unidade de bloco" do cartão do kanban, com o sinal invertido. `notaSemanaAtual()` é só um `reduce` de `pontos`, então soma automaticamente sem precisar de tratamento especial; o clamp de exibição (`Math.max(0, ...)` na barra do boletim) já existia. Editar o limite/peso ou desligar `negativa` reconcilia via excesso-antes/excesso-depois no salvar; apagar a meta estorna tudo (`estornarPenalidadesMetaRec`). Metas recorrentes **positivas continuam sem pontuar** — são só hábito/lembrete, como sempre foram.
- **Peso da meta**: `t.tagValor` (nenhum/baixo/médio/alto), padrão **alto**, multiplica a base do escopo — `metaPontosTotais` = `pontosMeta[escopo] × tagMultiplicador(peso)`. O padrão é alto de propósito: uma meta tem de pesar mais que uma etapa de rotina (padrão médio) e que um cartão do kanban do dia (padrão baixo). `reconciliarPesoDasMetas` roda no boot, estampa o peso nas metas antigas e acerta o crédito **em silêncio** (`sincronizarPontosMeta(t, true)`) — sem isso uma meta antiga ficaria mostrando "8 de 30 pts" até alguém tocar nela. As **áreas pré-prontas saíram** do formulário (`metaAreasPool` não sugere mais os `EIXOS`); `metaAreaInfo` continua resolvendo id de eixo para metas antigas.
- **Pontuação das metas é proporcional, item por item** (não mais tudo-ou-nada ao concluir): `metaPontosDevidos` = `metaPontosTotais × done/topics`, e `sincronizarPontosMeta` credita só o **delta** contra o que já foi pago. O crédito vai sempre para o período **corrente**, então uma meta que atravessa a virada do mês deixa em cada mês o que foi feito nele — por isso o razão é um mapa por período (`t.creditos = {periodo: pontos}`) e não um número só. Estorno maior do que o período corrente comporta desce para os anteriores (`aplicarDeltaMeta`), para `t.creditos` e `gam.metasPontos` nunca divergirem. `migrarCreditoMeta` converte metas pontuadas pela versão antiga (`t.pontuadaEm/pontuadaPeriodo/pontuadaPontos`) sem pontuar de novo.
- **Diário** (aba própria, `K_DIARIO`): um texto markdown por período, chaveado por `"dia:<ISO>"`, `"semana:<início configurado ISO>"`, `"mes:AAAA-MM"` ou `"ano:AAAA"` (`diarioChave`). A badge no topo troca o escopo e o input de data define o período. A tabbar tem 5 abas: Rotinas, Metas, Diário, Modelos, Dados. O botão "agenda" (▤, `#diAgenda`) existe em **todos os quatro escopos**, não só no dia — arrastar a página para a direita também abre. Não existe mais um botão "+ bloco": digitar a linha de markdown é o único jeito de criar um item de agenda, em qualquer escopo.
  - **Escopo "dia"**: linhas de checklist que começam com horário (`- [ ] 08:00 - 09:30 Tarefa`, `RE_TIMEBLOCK`) viram blocos numa grade por minuto (`agendaHtml`) — time-blocking no estilo do day-planner do Obsidian. Bloco **sem hora de fim é sempre entendido como 1h fixa** (não "vai até o próximo bloco" — isso mudou; um horário solto não é um compromisso do tamanho que sobrar até o item seguinte). Blocos sobrepostos dividem a largura em colunas (`distribuirColunas`).
  - **Escopos "semana"/"mês"/"ano"**: markdown próprio por escopo, cada um com seu regex (`RE_WEEKBLOCK` — `- [ ] seg 08:00 Reunião` ou `- [ ] qui Tarefa`, hora opcional; `RE_MONTHBLOCK` — `- [ ] 05 Consulta`, dia do mês 1-31; `RE_YEARBLOCK` — `- [ ] mar Renovar CNH`, mês abreviado), renderizados como lista agrupada por dia/dia-do-mês/mês (`agendaGrupoHtml`), não como grade — não há granularidade de minuto nesses escopos. `agendaHtmlPara(escopo, texto, iso)` é o dispatcher; todos os quatro escopos compartilham o mesmo toque-para-concluir e **arrastar para a direita marca como adiado** (`attachSwipeAdiar`, `data-agline`), porque a linha de origem no texto é sempre identificada pelo mesmo índice independente do escopo. A ordem dos dias da semana em `agendaSemanaHtml` segue `ordemDiasSemana()` (dia de início configurável, ver seção da semana).
- **Estado "adiado" no markdown**: `RE_CHECK` aceita `[>]` além de `[ ]`/`[x]` (mesma convenção do plugin Tasks do Obsidian); `estadoCheck(m)` devolve `aberto|feito|adiado` e é o único lugar que interpreta o caractere. `setCheckStateInText()` alterna um estado específico, `toggleCheckLineInText()` continua alternando aberto↔feito.
- **Áreas das metas**: texto livre com sugestões (`mountTagInput`), não uma lista fixa. `EIXOS` entra como sugestão e empresta a cor; digitar um nome novo cria a área. `metaAreaInfo(v)` resolve tanto id de eixo legado quanto rótulo livre (cor derivada por hash do nome).
- **Modelos**: um tipo por entrada em `TMPL_TYPES`; adicionar um tipo novo exige tocar em 5 pontos — `TMPL_TYPES`, `newTemplateDoc()`, o mapa de `renderTemplateDoc()`, `tmplMeta()` e `docToMarkdown()`+`mdTypeLabel()`. A tela de pastas separa em duas seções: as fixas (uma por tipo) e as **anotações de rotinas** (uma pasta por rotina que gera journaling) — `templateFolderTiles()` devolve `{ fixas, rotinas }`.
- **Registro de pontos** (`type:"scoreboard"`): placar de jogo com `players[{id,name}]`, `rounds[{id,scores:{playerId:número}}]` e `higherWins`. Uma única grade CSS: colunas = jogadores, linha Σ de totais logo abaixo dos nomes, linhas seguintes = turnos. As colunas são `minmax(0,1fr)` e a tipografia encolhe por densidade (`.compacto` a partir de 4 jogadores, `.mini` a partir de 6) — até 8 jogadores cabem na largura do celular sem rolagem horizontal. Digitar um ponto **não** repinta a grade (o input perderia o foco) — só `atualizarTotais()` roda. Célula vazia é "ainda não jogou", diferente de zero.
- **Data de criação**: toda nota (`K_NOTES`) e todo documento de modelo carregam `createdAt` imutável, exibido por `criadoEmHtml()` logo abaixo do título (`tmplHeader` e `renderNoteEditor`). Itens antigos foram retroalimentados com `updatedAt` no boot.
- **Kanban por escopo do Diário** (`K_DIAKANBAN`, abaixo da anotação, em **todos** os escopos: dia, semana, mês e ano): array de `{id,text,col,per,ord,tagValor,eixo,gamItemId|gamPeriodo+gamPontos}` com colunas `todo|doing|done` (`DIA_KB_COLS`). O campo **`per`** é a chave do período no formato de `diarioChave` (`"dia:2026-07-27"`, `"mes:2026-07"`) — um campo só que carrega escopo + período e ordena por comparação de string dentro do mesmo escopo (`escopoDoPer`, `perAtual`). Nasceu como `dia` e é migrado por `migrarKanbanParaPeriodo`. Cartão novo já nasce com `tagValor:"baixo"` (não "nenhum" — pontuar por padrão, sem exigir abrir o cartão à toa), tanto no "+ item" inline do board (`pintarKanban`, só quando `opts.pesos`) quanto no lançamento rápido do player. `eixo` é a área da roda da vida do cartão, mesma convenção de `r.eixo`/`t.eixo` — selecionada pelo componente compartilhado `pintarAreaChips(wrap, atual, onChange)` (também usado no editor de rotina), só aparece com `rodaAtiva()`. `pontosCartao(tag, per, area)` e `registrarConclusao("kanban", {..., area})` respeitam a fatia da área **só para dia/semana** (que entram na semana); mês/ano viram bônus em `gam.metasPontos`, que não tem repartição por área.
  - **Peso**: `tagValor`, padrão `"nenhum"` (pontuar é opcional). O cartão **não tem duração** — vale um bloco da duração de referência, então `pesoBruto(tag, config.divisorDuracao)` = o próprio multiplicador. `pontosCartao(tag, per)` multiplica ainda por `KB_ESCOPO_MULT` (`dia:1, semana:2, mes:3, ano:4`): escopo mais longo pesa mais.
  - **Para onde vão os pontos**: dia e semana entram na nota da **semana** (`registrarConclusao("kanban", …)`, itemId **estável** `kanban:<cardId>:<ISO>` para poder estornar; o `mult` entra no próprio `pb` para `repararFatorSemanaAtual` não perder o escopo). Mês e ano entram em `gam.metasPontos[periodo]`, junto das metas — é lá que o fechamento mensal/anual lê. Sair de "Feito" ou excluir estorna (`descreditarCartao` cobre os dois caminhos). Tudo passa por `sincronizarPontosCartao`, chamado dentro de `gravarKanban` — o único ponto de reconciliação. Cartão em `done` fica **cravado no dia** em que foi concluído; cartão aberto ou em andamento é pendência e `rolarPendenciasPara(iso)` traz para hoje tudo que ficou atrás — e só roda quando `iso === localKey()`, para navegar pelo histórico não reescrever o passado. `gravarDiaKanban(cols, iso)` trata as colunas como a verdade e reconcilia (adota cartões novos, remove os que saíram, regrava `ord`). O tabuleiro é o mesmo do modelo "kanban": `pintarKanban(body, cols, gravar)` — **não** duplicar a lógica de arrasto. Variante `.kb-inline` para tela que já rola.
  - **Abas de coluna** (`opts.abas`, só no kanban do Diário): segmentado no topo e **uma coluna por vez** (`kbAbaAtiva`), para não obrigar a rolar a aba inteira até "Feito". Com uma só coluna no DOM, a posição do elemento deixa de ser o índice em `cols` — por isso cada `.kb-col` carrega `data-colidx` e o arrasto lê dali, nunca do índice do array de elementos.
  - **Horário no cartão** (`opts.horarios`, `it.hIni`/`it.hFim`, só no escopo dia): cartão com hora vira bloco na agenda por `blocosDoKanban(iso)`, concatenado aos blocos da nota dentro de `agendaHtml` (que reordena antes de `distribuirColunas`, pois ela assume a lista ordenada). Bloco de cartão usa `data-agcard` (e não `data-agline`, que é índice de linha do texto) e o clique conclui/reabre o cartão. Sem hora de fim = 1h, mesma regra da nota.
  - **O "✕" da edição do cartão CANCELA, não exclui** (excluir é a lixeira ao lado). Isso só é possível porque **nenhum campo é escrito no cartão enquanto a edição está aberta** — tudo é lido no "ok". Ao mexer nos campos de edição, manter essa regra.
  - Cartão em duas linhas: `.kb-card-top` (alça + texto) e `.kb-card-bot` (horário, peso, botões). Em linha única o texto ficava espremido entre a alça e três botões.
- **Nota anexada à rotina** (`r.notaId` → uma nota de `K_NOTES`): escolhida no editor da rotina (`#edNota`), aberta no player por `openPlayerNotaOverlay()` **sem interromper a execução** — o timer segue correndo atrás. Abre em leitura (`renderMdBlock`, com checklist e toggle clicáveis) e o lápis troca para **textarea**, não para o editor contínuo: só existe um `liveCtx` por vez e ele pertence ao Diário/Notas (mesma razão das anotações de journaling). Id órfão (nota apagada) só faz o botão sumir — `notaDaRotina()` devolve null, sem migração.
- **Nota por ETAPA** (`s.noteId` → uma nota de `K_NOTES`, diferente de `r.notaId` que é da rotina inteira): vinculada em `openStepEditor` (seção "Nota da etapa", só escrita em `s` no "Salvar", mesma convenção do resto do editor de etapa) — escolhe uma nota existente ou cria uma em branco na hora (título automático via `nomeAutoDoc()`, conteúdo preenchido depois em Modelos → Notas simples). No player, some o botão "&#8599; nota"/"ver nota vinculada" (zen e normal) que abre `openNoteOverlay(step.noteId)`, **somente leitura** — para editar o conteúdo é preciso ir em Notas simples. Útil para lembretes específicos da etapa (ex.: qual baralho de flashcard estudar). Nota apagada só some o botão, sem migração (mesmo padrão de `r.notaId`).
- **Nome automático de nota/documento novo**: `nomeAutoDoc()` → `"AA-MM-DD-HHHH"`, usado em `newTemplateDoc()` (todos os tipos) e em `openNoteEditor(null)`. Ordena por data no app e no Finder (o espelho markdown usa o título como nome de arquivo). O doc `countdown` é exceção proposital: é o container único das Metas, não uma nota.
- **"Não fazer" uma etapa** (`K_NAOFEITAS`, `{[routineId]:{date,ids}}`): encerra a etapa sem concluir e sem pontuar (`naoFazerEtapa()` → `advanceStep(true, true)`) e a anota como pendência do dia. Reabrir a rotina hoje traz **só as pendentes** (filtro em `startPlayer` + `podarDescansos`, que evita descanso solto nas pontas). Concluir de verdade limpa a marca; `goPrevStep` desfaz. Vira o dia, o registro é descartado no boot. Diferente de "pular etapa (opcional)", que descarta a etapa sem repescagem. `skipRowHtml`/`wireSkipRow` montam os dois botões — usados pelo player **e** pelo modo zen, para não divergirem.
- **Android nativo** (`android/app/src/main/java/com/pedro/rotinas/`): `ShortcutsPlugin` (atalhos do launcher), `TimerOverlayPlugin`+`TimerOverlayService` (bolha do cronômetro sobre outros apps), `RoutineWidgetProvider`+`RoutineWidgetConfigActivity`+`RoutineStore` (widget por rotina). O widget e a tela de configuração leem as rotinas direto de `filesDir/brita/rotinas_v2_routines.json` via `RoutineStore` — não passam pela ponte JS. Plugins novos precisam de `registerPlugin()` em `MainActivity`.
- **Bolha do cronômetro** (`TimerOverlayService`) — três regras que já foram bug e não devem regredir: (1) só aparece com o app em **segundo plano** (`appEmSegundoPlano`, alimentado por `appStateChange` do Capacitor + `visibilitychange`); o serviço sobe junto com a rotina e o extra `visible` esconde apenas a *view*, porque Android 12+ proíbe iniciar foreground service em segundo plano. (2) o JS manda a **fila** das etapas seguintes (`filaOverlay()`) e o serviço consome sozinho as automáticas (só descansos, mesmo critério de `catchUpSteps`) — sem isso a bolha ficava presa na etapa anterior contando negativo, porque o WebView suspenso não avança nada. (3) No plugin, ler millis com `call.getData().optLong(...)` e **não** `call.getLong(...)`: este último só devolve o valor se o parser JSON já entregou um `Long`, e `remainingMs` cabe em int → chegava como `Integer` e virava 0 (era o cronômetro zerado ao pausar).
- **Sons/vibração** — dois mecanismos independentes, cada um cobrindo um plano diferente:
  - **Primeiro plano**: `stepTransitionCue()`/`timeUpCue()`/`finishCue()`/`alarmCue()` (WebAudio `beep()` + `navigator.vibrate`), disparados de dentro do player (ex.: `startTicking`, `rem<=0`). Respeitam `soundMode(routine)` — `r.sound`: `"normal"|"suave"|"mudo"` — mas a vibração dispara **sempre**, mesmo em "mudo" (só o beep é que é cortado).
  - **Segundo plano** (`sincronizarAlertaFundo`, chamada por `sincronizarPlayerBackground` — o novo ponto único que substituiu as chamadas diretas a `sincronizarOverlay`): como o WebView suspenso não roda essas funções, o aviso de "tempo da etapa/descanso acabou" em segundo plano usa `LocalNotifications` (não a bolha — que só existe se a preferência `K_OVERLAY` estiver ligada E a permissão de sobreposição concedida). Por isso é **independente** da bolha: funciona bastando a permissão de notificação (mesma de `syncNativeSchedules`). Agenda uma notificação one-shot por transição, encadeando os descansos automáticos seguintes (mesmo critério de `filaOverlay()`/`auto`, teto de 10), sempre cancelando e reagendando do zero (`cancelarAlertaFundo`) a cada chamada — tag própria `extra.brita:"stepAlert"` para não colidir com o cancela-e-resync de `syncNativeSchedules()` (que só mexe em `"sched"`). Dois canais Android pré-criados no boot (`ensureTimerAlertChannels`): `brita_timer` (som+vibração, `r.sound !== "mudo"`) e `brita_timer_mudo` (`importance:2`, sem som, só vibra). `pararOverlay()` também cancela esses alertas, independente de ter bolha ou não — é o ponto único de "player parou".
  - As notificações agendadas de rotina (`syncNativeSchedules`, horário de início) e de meta recorrente (janela de lembrete) já tocam som+vibração **de graça**: usam o canal `"default"` do plugin `@capacitor/local-notifications`, que o próprio plugin cria com `setSound()` do som padrão do sistema e `Notification.DEFAULT_ALL` quando nenhum `sound` custom é passado — não precisou de canal próprio.

```css

--line: #3A3632;      --text: #EDE7DD;       --muted: #8A8478;   /* cor "cinza escuro" dos ícones */
```

Tema claro é um override via classe `body.light` (mesmas variáveis, valores diferentes) — nunca hardcodar cor; sempre usar a variável CSS correspondente, para que os dois temas continuem funcionando. O claro é **cinza claríssimo neutro** (`--bg: #F3F5F8`) com superfícies brancas destacadas por `--shadow-1`; era bege (`#F6F2EC`) e o Pedro achou sem graça — não voltar para tons quentes. Ao mexer no claro, atualizar também o `content` do `<meta name="theme-color">` em `applyTheme()`.

Linguagem visual atual: superfície branca + sombra suave (não só borda de 1px), raio de `var(--radius)`, e **feedback de toque** com `transform: scale(...)` no `:active` (cards, `.icon-btn`, `.bell-btn`, `.play-btn`, `.btn-primary`, `.fab`). Seguir esse padrão em componente novo. O check de concluir etapa é verde (`.ctrl-btn.ok`), não gradiente.

## Regras de layout que já foram reclamação

- **Tabelas (`.dev-row`)**: a 1ª coluna é texto e fica com toda a sobra (`flex:1 1 auto`); as colunas de número têm largura **mínima fixa**, `text-align:right` e `tabular-nums`, para uma linha alinhar com a de cima. O `space-between` sozinho esticava a coluna do meio e cada linha saía torta. `.dev-row.dev-head` é o cabeçalho, `.dev-n.wide` a 3ª coluna com texto longo. Não voltar a deixar as colunas com a mesma largura.
- **Cabeçalho de aba não é fixo em NENHUMA aba.** Metas e Modelos usam `.tab-scroll` (um nó `flex:1; overflow-y:auto` que leva o `.home-header` junto); em Metas o corpo é `#metasBody`, irmão do cabeçalho dentro do `.tab-scroll`, porque `paint()` monta os cards com `innerHTML +=`. Em Dados e Diário o título e a navegação ficam **dentro** da área que rola — numa tela de celular, fixá-los comia a altura útil. Padrão: um nó de rolagem com `#statsHead`/cabeçalho + um nó de conteúdo irmão (`#statsBody`, `#diContent`). O conteúdo é irmão, e não o mesmo nó, porque as seções são montadas com `innerHTML +=` — no mesmo nó cada seção nova recriaria os botões do cabeçalho e derrubaria os handlers.
- **Busca global + Configurações no topo de TODAS as abas**, no nível do título e do lado oposto: `cfgBtnHtml()` (devolve os DOIS botões, lupa antes da engrenagem) no `.header-right` do `.home-header` + `wireCfgBtn(el)`. Não duplicar os botões nem os destinos. A busca abre em overlay (`openGlobalSearch()`, classe `.confirm-overlay.search-overlay`) e não inline: assim a mesma superfície serve as cinco abas sem nenhuma delas ter de reservar espaço para campo e resultados — e o voltar do Android a fecha via `closeTopOverlay()`.
